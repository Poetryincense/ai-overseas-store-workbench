# P1-03.5 — Engineering Baseline (before Scope Guard)

**Priority**: P0 (blocks P1-04)
**Estimate**: 1–1.5 engineering days
**Depends on**: P1-03 (CI confirmed green on 2026-11-22, run #10)
**Parallel**: no. Migrations and configuration are serial.

## 1. Goal

Put in place the decisions that are expensive to change after data exists: deployment profiles and configuration, the Redis and rate-limit design, security baseline, owner recovery, audit events, slug policy, and a backup drill.

## 3. Scope

### B1 — Configuration profiles and startup validation

- One schema in `packages/config` lists every variable with its profile requirement.
- Start-up fails with a message naming the missing or malformed variable.
- `NODE_ENV=production` enforces the rules in ADR-0002 §3.
- Acceptance: unit tests for local and production profiles; API refuses to start with a missing `DATABASE_URL`.

### B2 — Rate-limit store interface and Redis implementation

- `RateLimitStore` with `memory` and `redis` implementations (ADR-0003 §2).
- `RATE_LIMIT_STORE` validated at start-up. `memory` is refused in the production profile.
- `/health/ready` checks Redis when it is required, and reports `not_configured` otherwise.
- Acceptance: integration test against the local Redis binary; counters expire; memory store refuses production profile.

### B3 — Security baseline

- Security headers on Workbench and API responses: `Strict-Transport-Security` (production only), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `frame-ancestors 'none'`, and a Content-Security-Policy suitable for Next.js.
- Request body limit (for example 64 KB) and request timeout set explicitly.
- Login limits per ADR-0003 §3: 20 attempts per IP, and 5 failed passwords per account, then a 15-minute lock with the generic error.
- Session idle timeout: a session unused for 12 hours is refused, using `last_seen_at`. Absolute expiry stays at 7 days.
- `trustProxy` set only from `TRUST_PROXY` (ADR-0002 §5).
- Acceptance: header tests; account-lock test; idle-session test; proxy test showing a spoofed `X-Forwarded-For` from an untrusted address is ignored.

### B4 — Owner recovery

- Migration: `owner_recovery_codes` table.
- `owner:create` creates 10 recovery codes and prints them once.
- `owner:regenerate-recovery-codes` asks for the current password, then replaces all codes.
- `owner:recover` consumes one code, sets the new password, revokes all sessions and writes `owner.recovered` to the audit table.
- Acceptance: integration tests for a used code (rejected), a wrong code (generic failure), sessions revoked after recovery, and no plaintext codes in the database.

### B5 — Runtime proxy in Workbench

- Replace `rewrites()` with a Route Handler forwarding `/api/v1/*`.
- The handler forwards `Cookie`, `Origin`, `X-CSRF-Token` and `Content-Type`, and relays `Set-Cookie`.
- `API_INTERNAL_URL` is read at run time.
- Acceptance: the existing Playwright auth suite passes unchanged, and a test changes `API_INTERNAL_URL` without rebuilding.

### B6 — Backup and restore drill

- `scripts/db-backup.sh` writes a custom-format `pg_dump` with a timestamp, and checks the file is non-empty.
- `scripts/db-restore.sh` restores into an empty database given a dump path.
- Drill: back up the local workbench database, restore it into a new database, run `db:migrate:status` and the auth integration test against the copy.
- Acceptance: drill log committed under `docs/sprints/phase-1/`, with the commands and results.

### B7 — Audit events

- Migration: `audit_events` table with `id`, `workspace_id`, `actor_type` (`human` / `agent` / `system`), `actor_id` (nullable), `action`, `target_type`, `target_id`, `metadata` (JSONB, allow-list of keys), `request_id`, `created_at`.
- Index on `(workspace_id, created_at)`.
- Writer function used by login, logout, recovery and (later) project commands. Metadata must not contain secrets; the writer rejects keys outside the allow-list.
- Acceptance: integration tests that a successful login, a failed login and a recovery each produce one row with the right actor; the writer rejects a non-allow-listed key.

### B8 — Slug policy

- Migration per ADR-0005 §B, as a separate migration from B4 and B7 so it can be rolled back alone.
- Acceptance: tests that an active duplicate slug is refused, an archived project's slug can be reused, and restoring into a taken slug returns `409`.

## 4. Out of scope

- Any agent, model call, or external platform integration.
- Password change while logged in (not needed for V1; recovery covers the gap).
- Passkeys.
- Object storage.
- Choosing a cloud provider.

## 5. Order of work

1. B1 and B2 (configuration and store interface), since B3 depends on them.
2. B7 migration, then B4 migration (it writes audit events).
3. B8 migration, separately.
4. B3, B5, B6.

Each migration gets its own commit so it can be reverted by itself.

- All B1–B8 acceptance criteria met, with tests.
- ADR-0002, ADR-0003, ADR-0005 implemented as written; ADR-0004 audit rules reflected in B7.
- Runbook updated with the recovery procedure and the backup drill.
- CI green on the final commit.
- Completion report in the standard format from AGENTS §8.
